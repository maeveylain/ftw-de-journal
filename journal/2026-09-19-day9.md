## What I learned

### AM Sesh : From Development to Production
- Quick recap: last week's reflection question was "what does a trustable pipeline mean," today's version was "what does a RELIABLE pipeline mean" — feels like the same question but one level harder
- Big shift today: dev vs prod isn't about writing better code, it's a different question entirely. Dev asks "can I make it work," prod asks "can other people depend on it"
- VS Code = where we write code, GitHub = where we version and share it, Databricks = where the pipeline actually runs
- CI/CD (I was amazed and intimidated by this tool at first)
  - CI = is this change safe to merge in? (test it before it joins everyone else's code)
  - CD = can we reliably move this into production, every time, without someone manually checking it?
- CI/CD is not the same thing as GitHub Actions. GitHub Actions is just a tool that automates the process — the process itself (test → version → deploy) is the actual thing to understand first
- For data engineering, testing isn't just "does the code run," it's also "is the resulting data actually good" — passing code can still produce bad data
- The deployment loop isn't write → deploy → done, it's a loop: change → test → version → deploy → verify, and when it breaks: diagnose → fix → redeploy

### PM Sesh : Shipping!
- Shipping it isn't the finish line — the real question becomes "what happens when nobody's watching it run?"
- Production pipelines need to: orchestrate → monitor → recover → govern
- Orchestration = a pipeline is basically never just one script, it's a bunch of tasks that need to run in the right order with the right inputs at the right time
- My analogy for me to imagine it is being a head chef: making sure everyone does their job at the exact right time, in the exact right order, and handling problems if someone drops a pan.
- Don't HARDCODE. Example: "process May 2026" into your pipeline, it should be parameterized (process_date, month, source, environment) so the same pipeline can run for any date/source without rewriting anything
- Pipelines need a trigger to run at all: time, data arriving, an event, an upstream job finishing, or manual click of run
- Idempotency callback to week 8 — turns out that wasn't just an ingestion nice-to-have, it's literally what makes recovering from failures safe (you can just rerun without fear of duplicating everything)
- Monitoring 101: monitor both code if success and data if correct
- When something breaks: detect → diagnose → impact → recover → verify
- Governance doesn't need to be some huge framework — the Pareto version is basically 5 questions: can we find it (naming), understand it (docs), trust it (quality), control it (ownership/permissions), trace it (lineage)
- Naming actually matters more than I thought — good naming just straight up reduces how much explaining you have to do later

## Terms I am still learning
- JOB (the whole workflow) → TASK (one piece of it) → DAG (the map of what depends on what)
- DAG means Directed Acrylic Graph
- **Retry vs Rerun vs Backfill** retry = try the same failed thing again, rerun = redo a previous run, backfill = go back and process historical data that got missed
- **Data lineage** — tracing a number back to its source
- **Least privilege** — give access only to what's needed, nothing extra
- **dlt / dbt / Great Expectations / DuckDB** — tools mentioned for the extended homework, not yet explored
