## What I learned

### Ingestion Fundamentals (AM Sesh)
- Reflection prompt for the day: What does it mean to build a TRUSTABLE pipeline?
- **Data doesn't stand still** — yesterday your pipeline worked, but today new data arrives: some records are new, some changed, some are duplicates, some arrive late
- The ingestion mental model: SOURCE → INGEST → BRONZE → PROCESS → SILVER/GOLD, and every ingestion has to decide: what do we bring in? how often? what is new? what has changed? what have we already processed?
- **Batch vs Streaming**: Batch = data arrives in groups ("process today's transactions"). Streaming = data arrives continuously ("process transactions as they happen")
- **Full load vs Incremental load**: Full load reprocesses everything every time (before I always use this, re-running the whole table every time, which is wasteful in real life production). Incremental load only processes what changed — instead of reprocessing the total data, we only just process the new data that arrived. 
- Common signals for new data: timestamp, sequential ID, filename, partition/date, source change log (this is the "watermark" concept — the marker of what's already been processed)
- **Append vs Overwrite vs Merge** — three fundamental patterns for handling incoming data:
  - Append = just add (risk: duplicates if the same record shows up twice, e.g. via `UNION ALL`)
  - Overwrite = replace everything
  - Merge = INSERT new + UPDATE matched — handles both new and changed records in one step
- `MERGE INTO target USING incoming ON target.id = incoming.id WHEN MATCHED THEN UPDATE WHEN NOT MATCHED THEN INSERT` is the core merge pattern
- **SCD (Slowly Changing Dimensions)**:
  - Type 1 = keep the latest only (old value is replaced, history is gone)
  - Type 2 = keep the history (old row marked OLD with a date range, new row marked CURRENT)
- **CDC vs SCD**: CDC (Change Data Capture) = what changed in the source? SCD = how should we preserve that change in our model? CDC finds the change, SCD stores the change
- **Idempotency**: an idempotent pipeline can safely be rerun — running it once, twice, or many times produces the same result (no duplicate inserts from re-running after a failure)
- **Deduplication**: duplicates aren't always identical (e.g. same order_id but different status/timestamp) — use `QUALIFY ROW_NUMBER() OVER (PARTITION BY id ORDER BY updated_at DESC) = 1` to keep only the latest version per key
- **Late-arriving data**: an event can happen on one date but arrive in the pipeline on a later date — the pipeline has to decide which batch "owns" it (based on event_date, not arrival_date)
- **Design for failure, not just success** — Failure is an expected state, not an edge case
- **The Incremental Processing Decision** — every incoming record needs four questions answered: Is it new? Has it changed? Have I processed it before? Do I need its history?

### Where Does Data Actually Come From? (PM Sesh)
- Before we can transform data, we have to get it — common sources: Files, Databases, APIs, Websites, Streams. Each source needs a different ingestion pattern
- **Rule: don't scrape what you can download** — prefer the most stable interface: Official file/dataset → API → Database → Web Scraping (last resort)
- **Pattern 1 — File Ingestion**: common formats are CSV, JSON, Parquet. A whole folder can become a data source — process every new file that lands, not just one file by name
- **Pattern 2 — Database Ingestion**: applications store operational data in databases that keep changing. Don't query the entire database every time — use `WHERE updated_at > last_processed` instead of `SELECT * FROM orders`
- **Pattern 3 — API Ingestion**: Endpoint + Parameters → Response (usually JSON) → DataFrame. Real APIs have authentication, pagination, rate limits, errors, and timeouts to handle. Status codes matter: 200 = okay, 404 = not found, 429 = slow down (rate limited), 500 = server problem. Pagination is basically incremental ingestion *inside* an API — page 1, page 2, page 3... and the pipeline needs to track where it is and what to do if one page fails
- **Pattern 4 — Web Scraping**: Web Page → HTML → Scraper (e.g. `BeautifulSoup`) → Structured Data. Web scraping is fragile — a site's HTML structure can change without warning and silently break your scraper. Before scraping, ask: Can we access it? Are we allowed to? Should we?
- **Bronze means preserve what you received** — don't immediately transform external data into your final model; keep the raw response first
- **Data needs provenance** — for external data, capture metadata alongside the actual values: `source_system`, `source_file`/`source_url`, `ingested_at`, `batch_id`. Always ask: where did this row come from?
- **Schema drift happens** — a source can add columns, or even change a value's format (`temperature: 18.4` becoming `temperature: "18.4°C"`) without warning. Failing loudly (e.g. with an `assert`) is better than silently producing bad data
- Bottom line: whatever the source (Parquet, CSV, Database, API, Website), the same engineering questions always apply: What is new? What changed? Have I processed it? Is it valid? Can I safely rerun it? Where did it come from?
