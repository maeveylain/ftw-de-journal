## What I learned
### SQL vs Spark (AM Sesh) 
- SQL = what data I want. Spark = how it runs across different machines / execute at scale
- !! Scale is not just more data -> it is splitting the work across different nodes (machines) 
- Same logic can be written in SQL or PySpark — just different syntax, same result
- Cheat sheet: SELECT → .select(), WHERE → .filter(), GROUP BY → .groupBy(), JOIN → .join()
- Cluster basics: Driver = coordinator, Workers = do the actual work, Partitions = data chunks, Shuffle = moving data around (expensive!)
- Cheap ops: filter before select. Expensive ops: group by, join, sort (because of shuffling, data must move across partitions)
- Rule of thumb: Simplicity is the key! (Try SQL first before going to Spark) 
### DQ with SQL (PM Sesh)
- Just because your pipeline works fine, doesn't mean its KOReEK!
- 6 dimensions of quality: Complete, Valid, Unique, Consistent, Timely, Accurate
- 5 core check types: NULL, UNIQUE, RANGE/ACCEPTED VALUE, REFERENTIAL INTEGRITY, VOLUME
- Previously our group already include validation in our pipeline, but I learned that it is better to keep record of dq_check_results to better monitor the quality of your data pipeline. (Bonus learning: adding a dq dashboard)


## Terms I am still learning
- **delta lake** - the storage format under Databricks tables that makes raw files behave like a real database
- **DLT** - delta live tables; a framework where you declare what each pipeline table should look like so that Databricks automatically runs and orders the whole pipeline for you
- **CI/CD** - Continuous Integration / Continuous Deployment; automated process that tests and deploys your code every time you push changes
- **Referential integrity check** - confirms every foreign key actually exists in the table it's supposed to point to
